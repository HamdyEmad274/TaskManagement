1
تطور تخزين كلمات المرور — من الكارثة للأمان

أكتوبر 2013 — Adobe Systems. تسريب 153 مليون حساب مستخدم. كلمات المرور كانت مخزّنة بـ Plain Text — قابلة للقراءة مباشرة. كل شخص حمّل الملف شاف كلمة مرور كل مستخدم.

السؤال: ازاي تخزّن كلمة المرور بحيث لو الـ Database اتسرق، المهاجم ما يلاقيش حاجة مفيدة؟

الجيل الأول — Plain Text
كارثة

الـ Database اتسرق = كل كلمات المرور مكشوفة فوراً.

مفيش أي حماية.

الجيل التاني — MD5 / SHA هاش بسيط
غير كافي

بدل ما تخزن الكلمة، بتحسب الـ Hash وتخزّنه.

المشكلة: الـ MD5 سريع جداً — GPU حديث يحسب 200 مليار Hash في الثانية.

المهاجم بيستخدم Rainbow Table — جدول جاهز فيه الهاش لكل كلمة شائعة.

بيبحث عن الهاش المسروق في الجدول في أقل من ثانية.

الجيل التالت — Salted Hash
أحسن — لكن لسه مش كافي

بتضيف String عشوائي (الـ Salt) لكل مستخدم قبل الهاش.

نفس كلمة المرور لكل مستخدم تعطي هاش مختلف خالص.

بيبطّل الـ Rainbow Tables لأنها مبنيّة من غير الـ Salt.

المشكلة: Brute Force لسه ممكن — الـ SHA سريع ومهاجم يقدر يجرب ملايين الاحتمالات في الثانية.

الجيل الرابع — BCrypt (Key Stretching)
الصح

البطء هو الميزة — مش العيب.

بـ Cost Factor 12: كل هاش بياخد ~400ms.

من ناحية المستخدم: مش حاسس بالفرق عند اللوجين.

من ناحية المهاجم: بدل 200 مليار هاش في الثانية — بقى 2-3 هاش في الثانية. كلمة مرور ضعيفة بتاخد سنين تُكسر.

كل حاجة محتاجها للـ Verification موجودة في الـ String نفسه — مفيش حاجة تخزّنها منفصلة.

2
مشكلة الـ Sessions عند الـ Scale

بعد ما حللت مشكلة تخزين كلمة المرور، في سؤال تاني: ازاي السيرفر يعرف مين اللي بيعمل الـ Request ده؟

الطريقة التقليدية: الـ Sessions — السيرفر بيحفظ في ذاكرته إن المستخدم X اتسجل دخول، ويديه Cookie فيها Session ID.

بيشتغل كويس — على سيرفر واحد.

المستخدم يلوجن ──► Server A يحفظ Session في ذاكرته ──► يديه Cookie: session_id=abc123 Request تاني ──► Load Balancer ──► Server B Session مش موجودة هنا 401 Unauthorized ← المستخدم ابتدع يلوجن!

المشكلة الجذرية: السيرفر بيحتفظ بـ State. وأي State على سيرفر واحد مش موجودة على السيرفرات التانية.

الحلالمشكلة
Sticky Sessions — دايماً وجّه نفس المستخدم لنفس السيرفر السيرفر وقع = كل مستخدميه اتـlog out
Sessions في DB مشتركة كل Request بيعمل DB query — بطء وـbottleneck
Sessions في Redis بيشتغل، لكنه Service إضافي لازم تشغّله وتـscale
⚠ جذر المشكلة
مش Sessions بالذات هي المشكلة — المشكلة إن السيرفر بيتذكر. الحل: خلّي السيرفر ينسى — والمستخدم هو اللي يجيب إثبات هويته مع كل Request.

الـ JWT — الهوية المحمولة

الـ JWT هو String فيه 3 أجزاء مفصولة بنقط. المستخدم بيجيب الـ Token ده مع كل Request. السيرفر بيتحقق منه من غير ما يرجع لأي DB أو Session Store.

⚠ تحذير أمني مهم
الـ Payload مش مشفّر — هو Base64 بس. أي حد عنده الـ Token يقدر يقراه. ما تحطش فيه بيانات حساسة زي كلمة المرور أو رقم البطاقة. حط فيه بس: userId, role, expiry — وخلاص.
ليه الـ Signature هو القلب؟

سؤال: لو الـ Payload مقروء، مش المهاجم يغير "role":"User" لـ "role":"Admin"؟

الجواب: يقدر يغيّر الـ Payload — لكن الـ Signature هيبقى غلط. لأن الـ Signature محسوب من الـ Payload الأصلي + Secret Key اللي بس السيرفر عارفه. لما السيرفر بيحسب الـ Signature من جديد ويقارنه، هيلاقي اختلاف ويرفض الـ Token.

مشكلة الـ Revocation — الضعف المتأصل في الـ JWT

الـ JWT مش ممكن يتلغى قبل ما ينتهي وقته.

سيناريو: مستخدم اتسرق حسابه. المدير مسح الحساب من الـ DB. المهاجم لسه عنده Token صالح لمدة 23 ساعة. السيرفر بيشوفه صالح — مش بيرجع DB عشان يـcheck.

الحل العملي — Expiry قصير + Refresh Token
Access Token: ينتهي في 15 دقيقة ← Stateless, سريع Refresh Token: ينتهي في 7 أيام ← متخزّن في DB، قابل للإلغاء اللوجين: ← Access Token (15 دقيقة) ← Refresh Token (7 أيام) متخزّن في DB طبيعي: كل Request بيستخدم Access Token فقط ← مفيش DB Lookup Access Token انتهى: POST /auth/refresh + Refresh Token ← السيرفر بيـcheck الـ Refresh Token في DB ← لو صالح: يولّد Access Token جديد اللوجاوت: امسح الـ Refresh Token من الـ DB Access Token لسه صالح لـ 15 دقيقة كحد أقصى ← Trade-off مقبول
💡 في مشروعنا
حالياً بنعمل Access Tokens بس (60 دقيقة). الـ Refresh Tokens جاية في Block متقدم. الـ Trade-off معروف ومقبول — لو حساب اتسرق، المهاجم عنده ساعة كحد أقصى.
5
ترتيب الـ Middleware — غلطة واحدة تكسر كل حاجة

في الـ ASP.NET Core، الـ Request بيمشي خلال سلسلة من الـ Middleware بالترتيب. في Authentication وAuthorization، الترتيب حرفياً بيكسر الـ App لو غلط.

✗ غلط — نتيجة: 401 دايماً حتى مع Token صالح
app.UseAuthorization();     // بيشوف HttpContext.User ← فاضي
app.UseAuthentication();    // بيملي HttpContext.User ← متأخر جداً
✓ صح
app.UseAuthentication();    // بيقرأ الـ Token ويملي HttpContext.User
app.UseAuthorization();     // بيشوف HttpContext.User ← جاهز

UseAuthentication: بيقرأ الـ JWT Token من الـ Header، بيـverify الـ Signature، وبيحط الـ Claims في HttpContext.User.

UseAuthorization: بيشوف HttpContext.User ويقرر لو المستخدم عنده صلاحية الـ Endpoint ده.

لو عكستهم، الـ Authorization بيشوف User فاضي ويرجع 401 — حتى لو الـ Token صالح 100%.

ليه ClockSkew = TimeSpan.Zero؟

بالـ Default، الـ JWT بيسمح بـ 5 دقائق تسامح بعد انتهاء الـ Token. يعني Token انتهى الساعة 3 لسه شغّال لحد 3:05. ده بيهزّل الـ Security — لو مستخدم اتـlog out، الـ Window المفتوحة للمهاجم أطول.

ClockSkew = TimeSpan.Zero بتلغي التسامح ده — Token انتهى = انتهى فوراً. إنت كتبتها في الكود من غير ما طُلب منك — ده instinct سليم.
