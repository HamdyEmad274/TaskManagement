Result Pattern + Unit of Work

ما اللي بنيناه في الـ Block ده

  • Result<T> — نوع بيعبّر عن النجاح أو الفشل بدون Exceptions

1
ليه الـ throw للـ Business Logic غلط؟

أول ما بتكتب RegisterAsync، غريزتك الأولى: 

public async Task<UserResponse> RegisterAsync(RegisterUserRequest request)
{
    var existing = await _userRepository.GetByEmailAsync(request.Email);
    if (existing != null)
        throw new Exception("Email already taken");  // ← الطريقة الجونيور
}

وفي الـ Controller: 

try {
    var result = await _userService.RegisterAsync(request);
    return Ok(result);
}
catch (Exception ex) {
    return BadRequest(ex.Message);
}
المشاكل الحقيقية
  • الـ throw للحالات الطبيعية. "إيميل موجود" مش استثناء — هو حالة عمل متوقعة. الـ Exception للحاجات الغير متوقعة زي الـ DB down.
  • المطوّر التاني مش عارف. بتنظر لـ Signature الميثود وشايف Task<UserResponse> — مش عارف إنها ممكن تـthrow. الكومبايلر مش بيقولك. لو نسيت الـ try/catch، هيجي 500 على المستخدم.
  • الـ Exceptions غالية جداً. إنشاء Exception بياخد Stack Trace كامل — ده 100-1000 مرة أبطأ من إرجاع قيمة عادية. في API بيستقبل آلاف الـ Requests، ده فرق محسوس.
💡 القاعدة
الـ throw للحالات غير المتوقعة فقط — DB down، NullReference، الأشياء اللي المفروض ما تحصلش. الحالات المتوقعة — "إيميل موجود"، "Task مش لقيناها" — دي نتيجة عمل طبيعية، بنعبّر عنها في الـ Return Type.
2
تصميم الـ Result<T> — Railway-Oriented Programming

الفكرة: الميثود بيكون ليها مسارين — النجاح والفشل. الـ Caller مجبور يـcheck على أي مسار وصل قبل ما يستخدم القيمة.

RegisterAsync(request) ├── مسار النجاح ──► Result<UserResponse> { IsSuccess = true, Value = userResponse } └── مسار الفشل ──► Result<UserResponse> { IsSuccess = false, Error = "Email exists" }
التصميم اللي بنيته
public class Result
{
    public bool IsSuccess { get; }
    public bool IsFailure => !IsSuccess;
    public string Error { get; private set; }

    protected Result(bool success, string error)
    {
        // Invariant: success=true مع error = خطأ
        // Invariant: success=false بدون error = خطأ
        if (success && !string.IsNullOrEmpty(error))
            throw new InvalidOperationException("...");
        if (!success && string.IsNullOrEmpty(error))
            throw new InvalidOperationException("...");

        IsSuccess = success;
        Error = error;
    }

    public static Result Success() => new Result(true, string.Empty);
    public static Result<T> Success<T>(T value) => new Result<T>(value, true, string.Empty);
    public static Result Failure(string error) => new Result(false, error);
    public static Result<T> Failure<T>(string error) => new Result<T>(default!, false, error);
}

public class Result<T> : Result
{
    private readonly T? _value;

    public T Value => IsSuccess
        ? _value!
        : throw new InvalidOperationException("Cannot access value of a failed result.");

    protected internal Result(T value, bool success, string error) : base(success, error)
    {
        _value = value;
    }
}
القرارات التصميمية الذكية اللي اتخذتها
القرارالحكمة منه
Inheritance: Result<T> : Result IUserService عندها DeleteAsync مش بترجع قيمة — بترجع Task<Result>. باقي الميثودز بترجع Task<Result<T>>. الـ Inheritance بيخلي الاتنين يـshare نفس الـ IsSuccess و Error logic.
Constructor Guards (Invariants) مستحيل تعمل Result في حالة inconsistent — Success مع Error أو Failure بدون Error. ده مبدأ الـ Domain Invariants من DDD.
Value يـthrow لو IsSuccess=false لو حد نسي يـcheck IsSuccess وحاول يوصل للـ Value — بيـcrash بـ message واضح. أحسن من إرجاع null صامت بيظهر في مكان تاني غير متوقع.
protected internal Constructor ما حدش يقدر يعمل new Result<T>(...) من برّة الـ Assembly. لازم يستخدم Result.Success() أو Result.Failure() — Factory Methods فقط.
IsFailure Property إضافية مش في الـ Contract الأصلي — بس بتريح الـ Caller. if (result.IsFailure) أوضح من if (!result.IsSuccess).
3
الـ Services — قرارات مهمة في الـ Implementation
LoginAsync — نفس الـ Error للحالتين — ليه؟
var user = await _userRepository.GetByEmailAsync(request.Email);
if (user == null)
    return Result.Failure<string>("email or password is incorrect.");  // ← مش "User not found"

var passwordIsValid = _passwordHasher.Verify(request.Password, user.PasswordHash);
if (!passwordIsValid)
    return Result.Failure<string>("email or password is incorrect.");  // ← نفس الرسالة

لو رجّعت رسالتين مختلفتين — "User not found" و "Wrong password" — بتدي المهاجم معلومة: يعرف إن الإيميل ده موجود في قاعدة بياناتك. بيستخدم ده في هجمات الـ Enumeration — يجرب ملايين الإيميلات يعرف مين مسجّل عندك.

نفس الرسالة للحالتين = المهاجم مش عارف هل الإيميل موجود ولا لأ. ده security best practice — إنت طبّقته من غير ما طُلب منك.

UpdateStatusAsync — الـ Ownership Check
var task = await _taskRepository.GetByIdAsync(id);
if (task == null)
    return Result.Failure<TaskResponse>("Task not found.");

if (task.UserId != userId)                                    // ← ده الفرق عن CreateAsync
    return Result.Failure<TaskResponse>("Not authorized.");   // 403 في الـ Controller

task.UpdateStatus(request.Status);
await _taskRepository.UpdateAsync(task);
await _unitOfWork.SaveChangesAsync(cancellationToken);

CreateAsync ما فيهاش Ownership Check لأن المستخدم هو اللي بيعمل التاسك لنفسه. UpdateStatusAsync فيها لأن User A ممكن يبعت taskId لـ Task بتاعة User B. لازم نـcheck إن الـ Task دي فعلاً بتاعة المستخدم اللي بيطلب التعديل.

⚠ تحذير أمني
ده بيتسمى IDOR — Insecure Direct Object Reference. من أكتر الثغرات شيوعاً في الـ APIs. المهاجم بيغير الـ ID في الـ Request عشان يوصل لبيانات ناس تانيين. الحل: دايماً تـvalidate إن الـ Resource بتاعة صاحب الـ Request فعلاً.
4
الـ Unit of Work — مين المسؤول عن الـ Commit؟

السؤال: بعد _userRepository.AddAsync(user)، مين بيعمل SaveChangesAsync؟

الخيارالمشكلة
داخل الـ Repository نفسه بيكسر الـ Atomicity — لو الـ Service بتعمل AddUser وAddNotification في نفس العملية، الأول بيتحفظ فوراً. لو التاني فشل، الأول ما يرجعش.
IUnitOfWork في الـ Service لا مشكلة — الـ Service بتـcontrol متى بالظبط تتعمل الـ Commit.
ليه نفس الـ DbContext؟

الـ UserRepository، الـ TaskRepository، والـ UnitOfWork كلهم AddScoped. في نفس الـ Request، الـ DI Container بيديهم نفس instance الـ AppDbContext.

يعني الـ Repository بيضيف على Change Tracker معين، والـ UnitOfWork بيـsave نفس الـ Change Tracker ده. مش Change Tracker تاني فاضي.

HTTP Request يوصل ↓ DI Container بيعمل: AppDbContext (instance #1) UserRepository (يستخدم instance #1) UnitOfWork (يستخدم instance #1) UserService (يستخدم UserRepository + UnitOfWork) UserService: _userRepository.AddAsync(user) → Change Tracker of #1: [user: Added] _unitOfWork.SaveChangesAsync() → SaveChanges on #1 → INSERT في الـ DB ✓ HTTP Request ينتهي AppDbContext #1 يتdispose — Change Tracker يتمسح
الـ CancellationToken — ليه موجود؟

لما المستخدم يضغط Back في المتصفح وسط الـ Request — الـ CancellationToken بيـfire. لو مررته لـ SaveChangesAsync، الـ EF Core بيلغي الـ DB Operation فوراً. بدله، السيرفر بيفضل بيكمّل العملية حتى لو المستخدم مش مهتم بالنتيجة — ده هدر في الـ Resources.

إنت ربطته من الـ Service Method للـ UnitOfWork. ده الطريقة الصح.

أخطاء شائعة في الـ Block ده
MistakeConsequenceFix
Throwing exceptions for business failures Callers forget try/catch → 500 errors on predictable cases Return Result.Failure() for known business failures
Different error messages for "not found" vs "wrong password" Enables user enumeration attacks Return same error message for both login failure cases
No ownership check in UpdateStatusAsync IDOR vulnerability — any user can update anyone's tasks Always check task.UserId == requestingUserId
SaveChangesAsync inside Repository Partial commits — first write succeeds even if second fails Call _unitOfWork.SaveChangesAsync() in the Service
UnitOfWork registered as Singleton Holds a reference to a disposed DbContext after first request Always AddScoped for anything that wraps DbContext
Accessing Result.Value without checking IsSuccess InvalidOperationException at runtime Always check if (result.IsSuccess) before accessing result.Value
