API Controllers + Global Error Handling

HTTP Entry Points + Status Codes + Middleware Pipeline

  • UsersController — Register, Login, GetById, GetAll, Delete
  • TasksController — Create, GetById, GetAll, UpdateStatus

1
الـ Controller — مسؤوليته الوحيدة

السيرفيس جاهز — بيعمل الـ Business Logic ويرجع Result<T>. الـ Controller مش بيعمل Business Logic. هو بس الـ Translator.

HTTP Request يوصل ↓ [Controller Action] 1. استلم الـ Request Body / Route Params 2. استخرج userId من الـ JWT (لو محتاج) 3. استدعي الـ Service 4. ترجم الـ Result لـ HTTP Response (Status + Body) 5. ارجع الـ Response ↓ HTTP Response يطلع

مش من مسؤوليته:

  • أي Business Logic — "هل الإيميل ده موجود؟" — ده في الـ Service
  • الكلام مع الـ Repository مباشرة
  • الـ try/catch للـ Unexpected Exceptions — ده في الـ Middleware
💡 التمييز العملي
لو كتبت سطر في الـ Controller وفكّرت "ده بيتعلق بقاعدة عمل" — انقله للـ Service. الـ Controller يفضل thin — خفيف.
2
HTTP Status Codes — لغة الـ REST

الـ Status Code مش مجرد رقم — هو جزء من الـ Contract مع الـ Client. الـ Frontend، الـ Mobile App، أي حد بيستهلك الـ API بيبني كوده على الـ Status Code. لو بعتله 200 على Error — كوده هيكسر.

السيناريوالـ Statusليه ده تحديداً
تسجيل مستخدم جديد ناجح 201 Created Resource اتعمل — مش بس طلب اتنفّذ. فرق مهم.
Login ناجح / Get بيانات 200 OK طلب ناجح وفيه body ترجع
Delete ناجح 204 No Content ناجح — مفيش حاجة ترجعها
إيميل موجود عند Registration 409 Conflict Resource موجود فعلاً — مش مجرد Input غلط
Login فشل (بيانات غلط) 401 Unauthorized فشل في إثبات الهوية
Task مش موجودة 404 Not Found Resource مش موجود
Task موجودة لكن مش بتاعتك 403 Forbidden أنا عارف مين إنت — بس مش مسموحلك
DB crash غير متوقع 500 Internal Server Error غلطة منّا — مش من المستخدم
الفرق بين 401 و 403

ده أكتر سؤال بيتغلط فيه في الـ Interviews:

  • 401 Unauthorized — مش عارف مين إنت. إبعت Token. (مسمّاه Unauthorized لكن معناه Unauthenticated — naming mistake تاريخي في المعيار)
  • 403 Forbidden — عارف مين إنت — بس إنت مش مسموحلك تعمل ده. مثلاً: user عادي بيحاول يوصل لـ admin endpoint، أو بيحاول يعدّل Task مش بتاعته.

في مشروعنا: Task موجودة لكن task.UserId != requestingUserId → 403 مش 404. بعض الـ APIs بيرجعوا 404 هنا عشان ما يكشفوش وجود الـ Task للمهاجم — ده valid trade-off تقدر تناقش فيه في Interview.

200 vs 201 — ليه يهم؟

201 Created بييجي عادةً مع Location Header بيقولك فين الـ Resource الجديدة: 

HTTP/1.1 201 Created
Location: /api/users/a1b2c3d4-...

الـ Frontend بيقدر يعمل GET على الـ Location ده تلقائياً. 200 OK ما بيقدّمش ده.

3
استخراج userId من الـ JWT داخل الـ Controller

لما المستخدم بيبعت Request مع JWT Token، الـ Authentication Middleware بيـparse الـ Token ويحط الـ Claims جوا HttpContext.User. الـ Controller بيقراهم من هناك — مش بيـparse الـ Token بنفسه.

JWT في الـ Header ↓ UseAuthentication() Middleware يـverify الـ Signature يـdecode الـ Payload يملي HttpContext.User بالـ Claims ↓ Controller Action يشتغل HttpContext.User.FindFirstValue(ClaimTypes.NameIdentifier) → "a1b2c3d4-e5f6-..." (الـ userId اللي حطيناه جوا الـ Token)
الكود
// داخل الـ Controller Action (بعد [Authorize])
var userIdString = User.FindFirstValue(ClaimTypes.NameIdentifier);
var userId = Guid.Parse(userIdString!);

ClaimTypes.NameIdentifier هو نفس الـ Claim اللي JwtTokenGenerator حطّ فيه الـ userId لما ولّد الـ Token. لو استخدمت اسم مختلف في التوليد، لازم تستخدم نفس الاسم في الاستخراج.

⚠ مهم
User.FindFirstValue() بترجع null لو الـ Claim مش موجود. الـ ! بتقول للـ Compiler "أنا متأكد مش null" — لأن لو فيه [Authorize] والـ Token valid، الـ Claim لازم يكون موجود. لو مش متأكد — check على null أو استخدم Guid.TryParse.
Helper Method — نظّف الـ Controller

لو عندك عدة Actions بتعمل نفس استخراج الـ userId، حطّ helper في الـ Base Controller: 

protected Guid GetCurrentUserId()
    => Guid.Parse(User.FindFirstValue(ClaimTypes.NameIdentifier)!);
4
GlobalExceptionMiddleware — الحارس الأخير

الـ Result.IsFailure بيتعامل مع الأخطاء المتوقعة. لكن في أخطاء غير متوقعة — DB connection انقطع، NullReference في مكان ما، memory overflow. دي بترمي Exception وتطلع من الـ Action.

من غير Middleware: ASP.NET Core بيرجع صفحة HTML بيها stack trace كامل — كود مصدري، paths، كل حاجة. ده Security vulnerability في Production.

Request ↓ [GlobalExceptionMiddleware] ← بيـwrap كل حاجة ↓ Authentication ↓ Authorization ↓ Controller Action ─── throw new Exception("DB connection failed") ↑ بيطلع لأعلى عبر الـ pipeline ↑ [GlobalExceptionMiddleware] بيمسكه هنا يـlog الـ Exception كاملة (للـ Developers) يرجع للـ Client: 500 ProblemDetails نظيف (بدون details)
الشكل المثالي للـ 500 Response

ما بيتبعتش للـ Client: 

// ❌ ما يوصلش للـ Client أبداً
"StackTrace": "at Microsoft.EntityFrameworkCore.DbContext.SaveChangesAsync...\n
               at TaskManagement.Infrastructure.Persistence.UnitOfWork..."

اللي بيوصل للـ Client (ProblemDetails): 

// ✓ اللي يوصل
{
  "type": "https://tools.ietf.org/html/rfc7807",
  "title": "Internal Server Error",
  "status": 500,
  "detail": "An unexpected error occurred. Please try again later."
}

الـ Exception الكاملة (message + stack trace) بتتـlog على السيرفر — الـ Developer يقدر يشوفها. الـ Client يشوف رسالة عامة فقط — المهاجم ما يعرفش أي حاجة عن الـ Infrastructure.

ترتيب الـ Registration في Program.cs
// ✓ الترتيب الصح — الـ Middleware الأول في الـ Pipeline
app.UseMiddleware<GlobalExceptionMiddleware>();  // ← أول حاجة
app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
💡 ليه أول حاجة؟
لأنه لو جه بعد Authentication مثلاً، وحصل Exception في الـ Authentication نفسها — الـ Middleware مش هيمسكه. لازم يكون في أول الـ Pipeline عشان يغطي كل الـ Stages.
5
Problem Details — الـ Standard الصناعي لـ Error Responses

APIs كتير بترجع errors بأشكال مختلفة — string، array، nested object. الـ Client مش عارف يـparse إيه. RFC 7807 هو الـ Standard العالمي اللي بيقول شكل الـ Error Response لازم يبقى كده: 

{
  "type": "https://tools.ietf.org/html/rfc7807",  ← نوع المشكلة (URL للدوكيومنتيشن)
  "title": "Conflict",                             ← اسم المشكلة
  "status": 409,                                   ← نفس الـ HTTP status
  "detail": "Email already exists.",               ← وصف قابل للقراءة البشرية
  "instance": "/api/users/register"                ← الـ endpoint اللي حصل فيه
}

الـ ASP.NET Core عنده built-in support — ControllerBase ورث methods زي: 

return Problem(
    detail: result.Error,
    statusCode: StatusCodes.Status409Conflict,
    title: "Conflict"
);

أو أبسط: 

return Conflict(new { error = result.Error });    // بسيط لكن مش standard shape
return Problem(result.Error, statusCode: 409);    // ✓ Problem Details
⚠ في مشروعنا
استخدام BadRequest(result.Error) شائع ومقبول في المشاريع الصغيرة. لكن في Production APIs أو لما تتكلم في Interview — اتكلم عن Problem Details وإنك تعرف الـ Standard.
6
الـ Pipeline — الترتيب الكامل في Program.cs

بعد Block 6، الـ Program.cs لازم يبقى بالشكل ده بالظبط: 

// --- Services Registration ---
builder.Services.AddControllers();          // ← لازم موجود عشان الـ Controllers تشتغل
builder.Services.AddOpenApi();
builder.Services.AddInfrastructure(builder.Configuration);
builder.Services.AddAuthentication(...).AddJwtBearer(...);
builder.Services.AddAuthorization();

// --- Middleware Pipeline (الترتيب مهم جداً) ---
var app = builder.Build();

app.UseMiddleware<GlobalExceptionMiddleware>();  // 1 — الأول دايماً
app.UseHttpsRedirection();                       // 2
app.UseRouting();                                // 3
app.UseAuthentication();                         // 4 — قبل Authorization
app.UseAuthorization();                          // 5 — بعد Authentication
app.MapControllers();                            // 6 — يربط الـ Routes
app.Run();

كل سطر في الترتيب ده ليه سبب. نقل أي سطر = سلوك مختلف أو error مش واضح السبب.

الـ Middlewareمسؤوليتهلو اتأخّر
GlobalExceptionMiddleware يمسك كل Exception غير معالجة Exception في أي middleware قبله تفلت
UseAuthentication يقرأ الـ JWT ويملي HttpContext.User HttpContext.User بيكون فاضي
UseAuthorization يشوف HttpContext.User ويطبّق [Authorize] بيشوف User فاضي → 401 دايماً
MapControllers يربط الـ HTTP Routes بالـ Controller Actions كل الـ Requests ترجع 404
!
أخطاء شائعة في الـ Block ده
MistakeConsequenceFix
try/catch in every Controller Action Same boilerplate repeated 10+ times, inconsistent responses Move to GlobalExceptionMiddleware
Returning 200 for business failures Client has to parse the body to know if it succeeded — breaks REST contract Map Result.IsFailure to the correct status code
Returning 401 when the user is authenticated but not authorized Client thinks it's a token problem, retries login — wrong signal 401 = not authenticated, 403 = authenticated but forbidden
Leaking stack trace in 500 response Exposes internal paths, library versions, SQL queries to attackers Log full exception server-side, return generic message to client
Injecting Repository directly into Controller Business logic ends up in Controller, untestable, violates Clean Architecture Always inject the Service interface
Missing AddControllers() in Program.cs All endpoints return 404 — confusing because there's no error message Add builder.Services.AddControllers() in service registration
Parsing userId from JWT manually in Controller Fragile, repetitive, wrong — AuthMiddleware already did this work Use User.FindFirstValue(ClaimTypes.NameIdentifier)
