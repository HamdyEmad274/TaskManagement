1
الـ EF Core Change Tracker — ازاي بيشتغل

الـ DbContext مش بس وصلة لقاعدة البيانات — هو بيتتبع كل Entity لمستها من إمتى ما اتعمل الـ Request. ده بيتسمى الـ Change Tracker.

كل Entity عندها حالة في الـ Tracker:

الحالةمعناهاالـ SQL اللي بيتولد
AddedEntity جديدة مش موجودة في الـ DBINSERT
ModifiedEntity موجودة واتغير فيها حاجةUPDATE
DeletedEntity محددة للمسحDELETE
UnchangedEntity اتقرأت من الـ DB ومحدش لمسهالا شيء
DetachedEntity مش متتبعة خالصلا شيء

لما بتعمل AddAsync(entity) — بيتحط في الـ Tracker بحالة Added بس. مفيش SQL بيتنفذ لحد ما تعمل SaveChangesAsync().

لما بتعمل SaveChangesAsync() — الـ EF Core بيشوف كل Entity في الـ Tracker، بيولد الـ SQL المناسب، وبيحطهم كلهم في Transaction واحدة.

AddAsync(user) → Change Tracker: [user: Added] AddAsync(task) → Change Tracker: [user: Added] [task: Added] SaveChangesAsync() → BEGIN TRANSACTION INSERT INTO Users ... INSERT INTO TaskItems ... COMMIT
✓ الفايدة
لو الـ INSERT الأول نجح والتاني فشل — الـ Transaction كلها بتـRollback. مش ممكن User يتخزن من غير Task أو العكس لو الاتنين في نفس الـ Operation. ده هو الـ Atomicity — الـ A في ACID.
2
Fluent API — ليه مش Data Annotations؟

عندك طريقتين تقول للـ EF Core ازاي يـmap الـ Entity على قاعدة البيانات.

الطريقةالمكانالمشكلة
Data Annotations جوا الـ Entity نفسها كـ Attributes الـ Domain Layer بتعرف عن الـ Database — ده ينكسر الـ Clean Architecture
Fluent API في الـ Infrastructure في كلاس Configuration منفصل لا شيء — هو الصح
✗ خطأ
// في Domain/Entities/User.cs — خطأ
[Required]
[MaxLength(100)]
[Column("UserName")]
public string Name { get; private set; }
✓ صح
// في Infrastructure/Persistence/Configurations/UserConfiguration.cs
public class UserConfiguration : IEntityTypeConfiguration<User>
{
    public void Configure(EntityTypeBuilder<User> builder)
    {
        builder.ToTable("Users");
        builder.HasKey(u => u.Id);
        builder.Property(u => u.Name).IsRequired().HasMaxLength(100);
        builder.Property(u => u.Role).HasConversion<string>();
    }
}

الـ HasConversion<string>() بتقول للـ EF Core: خزّن الـ Enum كـ string في الـ Database مش كـ int.

⚠ ليه String مش Int؟
لو خزنت UserRole.Admin كـ 1 وبعدين أضفت Role جديدة في الأول، كل الـ values في الـ DB اتغير معناها. لو خزنتها كـ "Admin"، المعنى واضح وثابت بغض النظر عن ترتيب الـ Enum.
ازاي الـ Configurations بتتطبق تلقائياً؟
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.ApplyConfigurationsFromAssembly(Assembly.GetExecutingAssembly());
}

السطر ده بيقول للـ EF Core: ابحث في الـ Assembly الحالية عن كل كلاس بينفّذ IEntityTypeConfiguration<T> وطبّقه تلقائياً. مش محتاج تسجّل كل Configuration بيدك.

3
Repository Pattern — ليه طبقة زيادة فوق EF Core؟

السؤال المنطقي: EF Core نفسه فيه كل حاجة — DbContext، LINQ، SaveChanges. ليه بنعمل Repository Pattern فوقيه؟

السببالشرح
إخفاء الـ EF Core عن الـ Application الـ Service مش المفروض تعرف إن في EF Core — تعمل Interface وخلاص
سهولة الـ Testing في الـ Unit Tests بتعمل Mock للـ Interface بدل ما تشغّل Database حقيقية
Reusable Queries بدل ما تكتب نفس الـ LINQ في كل مكان، بتحطه في Repository مرة واحدة
بدل الـ DB بسهولة تقدر تغير من SQL Server لـ MongoDB من غير ما تلمس أي Service
مثال على الفرق
✗ بدون Repository — الـ Service عارفة بـ EF Core
// Application/Users/Services/UserService.cs — خطأ في Clean Architecture
public async Task<UserResponse> GetByIdAsync(Guid id)
{
    var user = await _context.Users                 // DbContext جوا الـ Application
        .FirstOrDefaultAsync(u => u.Id == id);
    // ...
}
✓ مع Repository — الـ Service عارفة بـ Interface بس
// Application/Users/Services/UserService.cs — صح
public async Task<Result<UserResponse>> GetByIdAsync(Guid id)
{
    var user = await _userRepository.GetByIdAsync(id);  // Interface بس
    // ...
}
💡 ملاحظة مهمة
الـ Repository مش بتحل كل المشاكل — في حالات معقدة زي الـ Reporting، أحياناً الأحسن تكتب SQL مباشرة. الـ Repository مش دين — هو أداة. استخدمه لما بيبسّط الكود، مش لما بيعقده.
4
Migrations — ازاي الـ EF Core بيعمل الـ DB Schema

الـ Migration هي ملف C# بيوصف التغيير في الـ Schema — مش الـ Schema كله. يعني لو أضفت Column جديدة، الـ Migration بتقول "أضف العمود ده" — مش "أعيد بناء الـ Table كله".

Model (C# Classes) ↓ Migration File ↓ Database Schema
التسلسل الصح
  • غيّر في الـ Entity أو الـ Configuration
  • شغّل dotnet ef migrations add MigrationName
  • EF Core بيقارن الـ Model الحالي بالـ Snapshot السابق ويولّد الـ Migration
  • شغّل dotnet ef database update عشان تطبق الـ Migration على الـ DB
⚠ تحذير
ما تعدّلش في ملف Migration بعد ما اتعمل database update. لو محتاج تغيير — اعمل Migration جديدة. التعديل اليدوي بيكسر الـ Snapshot ويخلي الـ DB في حالة غير متسقة.
الـ DbContextModelSnapshot — ليه موجود؟

الـ EF Core بيحتفظ بـ Snapshot من آخر حالة للـ Model. لما تعمل Migration جديدة، بيقارن الـ Model الحالي بالـ Snapshot ده عشان يعرف إيه اللي اتغير. من غيره، مش هيعرف إيه الجديد وإيه القديم.

5
تسجيل الـ Services — AddScoped vs AddSingleton vs AddTransient

لما بتسجّل Service في الـ DI Container، بتقرر كام مرة بتتعمل Instance منها.

LifetimeInstance جديدة لما؟استخدام في مشروعنا
AddSingleton مرة واحدة طول عمر الـ Application حاجات stateless وما بتتغيرش — لكنه مش الـ Default
AddScoped مرة لكل HTTP Request كل حاجة عندنا — DbContext, Repositories, Services, UnitOfWork
AddTransient كل مرة يتطلب منها نادر — للـ lightweight stateless operations
ليه كل حاجة عندنا Scoped؟

الـ AppDbContext لازم يكون Scoped لأنه بيحتفظ بـ Change Tracker خاص بكل Request. لو كان Singleton، كل الـ Requests هتشارك نفس الـ Change Tracker وده كارثة — Entity من Request A ممكن تتبعت في Request B.

وبما إن UnitOfWork وUserRepository بيـwrap نفس الـ DbContext، لازم يكونوا نفس الـ Lifetime — Scoped. لو UnitOfWork كان Singleton وـDbContext Scoped، الـ Singleton هيتمسك بـ DbContext اتدمر بعد أول Request.

⚠ قاعدة الـ Lifetime
أي Service بتـinjected فيها Service تانية — لازم الـ Outer يكون نفس الـ Lifetime أو أقصر. Singleton لا يحتوي Scoped. Scoped لا يحتوي Transient بمشاكل. الأأمن: خلي كل حاجة Scoped إلا لو عندك سبب قوي.

MistakeWhy It's WrongFix
DbContextOptions without generic EF Core can't identify which context to configure Use DbContextOptions<AppDbContext>
Calling SaveChangesAsync inside Repository Breaks atomicity — partial commits can't be rolled back Use IUnitOfWork.SaveChangesAsync() in the Service
Data Annotations on Domain Entities Domain layer learns about the database — violates Clean Architecture Use Fluent API in Infrastructure Configurations
Registering DbContext as Singleton Shared Change Tracker across requests — race conditions and data corruption Always AddDbContext<T> which is Scoped by default
