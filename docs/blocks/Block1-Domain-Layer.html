Clean Architecture — ليه 4 Projects؟

الـ Clean Architecture بتنظم الكود في طبقات، وكل طبقة بيكون عندها مسؤولية واحدة بس. القاعدة الأساسية اللي بتبنى عليها كل حاجة هي:

الطبقات الداخلية ملهاش أي علم بالطبقات الخارجية.

يعني الـ Domain مش عارف إن في EF Core موجود. والـ Application مش عارف إن في SQL Server. بس الـ Infrastructure والـ API عارفين بكل حاجة لأنهم الطبقات "الوسخة" اللي بتتعامل مع العالم الخارجي.

API ──► Application ──► Domain │ ▲ └──► Infrastructure ─────┘
الـ 4 Projects وليه كل واحدة موجودة
Project مسؤوليتها بتعرف مين؟
Domain الـ Entities والـ Business Rules والـ Contracts مش عارفة حاجة — قلب المشروع
Application الـ Use Cases والـ DTOs وال Service Interfaces الـ Domain بس
Infrastructure DB, Redis, JWT, File System الـ Application
API HTTP Endpoints, Middleware, DI Wiring الـ Application + Infrastructure
ليه ده مهم عملياً؟
  • تقدر تبدل قاعدة البيانات من SQL Server لـ PostgreSQL من غير ما تلمس أي حاجة غير الـ Infrastructure
  • تقدر تعمل Unit Tests للـ Application وال Domain من غير ما تشغل Database حقيقية
  • تقدر تبدل الـ Web Framework من غير ما تلمس الـ Business Logic

الـ Domain Layer — الكيانات والـ Enums
الـ Entities — إيه الفرق بينها وبين أي Object تاني؟

الـ Entity هي Object عندها هوية — بتتعرف بالـ Id بتاعها مش بقيمها.

مثال: لو عندك User اسمه "أحمد" وغيرت اسمه لـ "محمد"، هو لسه نفس الـ User. الهوية في الـ Id مش في الاسم. ده الفرق بين Entity وValue Object. الـ Value Object بيتعرف بقيمه — زي الـ Email مثلاً: لو email عندك هو نفس email تاني، هما نفس الحاجة، حتى لو objects مختلفة.

الـ BaseEntity — ليه Guid مش int؟
public class BaseEntity
{
    public Guid Id { get; private set; }
    public DateTime CreatedAt { get; private set; }
}
  • الـ int متسلسل ومتوقع — حد يقدر يخمن user/1, user/2 وده ثغرة أمنية
  • الـ Guid مش قابل للتخمين — بيتولد عشوائياً
  • الـ Guid يشتغل في الأنظمة الموزعة — مفيش تعارض لو أكتر من سيرفر بيولد IDs في نفس الوقت
ليه private set؟

الـ Entity المفروض تتحكم في حالتها هي. ما ينفعش حاجة من بره تعمل entity.Id = شيء تاني. ده مبدأ الـ Encapsulation في DDD.

⚠ تنبيه مهم
الـ EF Core بيحتاج يحط قيم في الـ Properties لما بيقرأ من قاعدة البيانات — وده بيتعارض مع الـ private set. الحل في Block 3: هنكلم EF Core يستخدم الـ Reflection عشان يتجاوز الـ private setter. ده سلوك مدعوم في EF Core وما فيهوش أي مشكلة.
الـ Enums — ليه أرقام صريحة؟
public enum TaskPriority
{
    Low    = 1,
    Medium = 2,
    High   = 3
}
  • بدون قيم صريحة، الـ C# بيبدأ من 0 تلقائياً — Task من غير Priority هيبقى Low بالغلط
  • بالقيم الصريحة، 0 معناها "مش محددة" و1 معناها Low — قصدي ومقصود
  • لو رتبت الـ Enum من جديد في المستقبل، القيم المخزنة في قاعدة البيانات مش هتتأثر
ليه غيرنا TaskStatus لـ AppTaskStatus؟

TaskStatus اسم موجود فعلاً في .NET جوه System.Threading.Tasks — وده بيتعلق بحالة الـ async Task. لما بتفعّل ImplicitUsings، الـ System.Threading.Tasks بيتضاف تلقائياً. فلو سميت الـ Enum بتاعتك TaskStatus، الكومبايلر بيشوف اتنين بنفس الاسم ويطلع خطأ "Ambiguous Reference". الحل البسيط: اديه اسم مختلف زي AppTaskStatus.

Repository Interfaces — ليه في الـ Domain؟
public interface IUserRepository
{
    Task<User> GetByIdAsync(Guid id);
    Task<IEnumerable<User>> GetAllAsync();
    Task AddAsync(User user);
    Task DeleteAsync(User user);
}
الـ Dependency Inversion Principle — أهم مبدأ هنا

ده الحرف D في SOLID. بيقول:

الطبقات العليا (Domain/Application) ما تعتمدش على الطبقات الدنيا (Infrastructure) — الاتنين يعتمدوا على Abstractions.

يعني إيه عملياً؟ الـ Domain بيقول "أنا محتاج حاجة تعمل GetUser" فبيعرّف الـ Interface. الـ Infrastructure بتوفر الـ Implementation الحقيقية باستخدام EF Core. الـ Domain ما شافش EF Core خالص — ما عندوش أي Reference ليه.

✓ الفكرة
Domain بيعرّف إيه اللي محتاجه → IUserRepository
Infrastructure بتوفر إزاي تعمله → UserRepository : IUserRepository
الـ DI Container بيربطهم ببعض وقت الـ Startup
ليه كل الـ Methods بترجع Task<>؟

أي حاجة بتتكلم مع قاعدة البيانات — ده I/O. والـ I/O بياخد وقت.

  • Sync: الـ Thread بيفضل واقف مستنى — بيضيع resources ومش قادر يخدم requests تانية
  • Async: الـ Thread بيتحرر وهو مستنى — يرجع لما الداتا جاهزة — التطبيق بيـscale أحسن

القاعدة: أي method بتتكلم مع DB أو File أو Network أو Redis — لازم تكون Async وترجع Task<>.

ليه IEnumerable<User> مش List<User>؟

الـ List<T> هو Implementation محدد — بيجبر المستخدم على نوع معين. الـ IEnumerable<T> هو Abstraction — بيقول "حاجة قابلة للـ iteration بس". ده بيديك مرونة في الـ Implementation ومش بتـexpose تفاصيل داخلية.

4
DomainException — الـ Custom Exception
public class DomainException : Exception
{
    public DomainException(string message) : base(message) { }
}

ليه مش بستخدم Exception العادية بدل ما أعمل Custom Class؟

  • بأعمل catch (DomainException) وأرجع 400 Bad Request تحديداً
  • مش بـcatch الـ SqlException وأرجع 400 — دي error تانية خالص وترجع 500
  • في Block 5 هنعمل Global Exception Handler بيشوف نوع الـ Exception ويقرر الـ HTTP Status Code المناسب
مثال عملي — هيجي في Block 5
// في الـ Service
if (await _taskRepo.ExistsSameTitleTodayAsync(request.Title, userId))
    throw new DomainException("A task with this title already exists today.");

// في الـ Global Exception Handler
catch (DomainException ex)
    return BadRequest(ex.Message);  // 400
💡 ملاحظة
ده بيخلي الـ Business Rule Violations (زي تكرار العنوان) تـreturn 400، وأي Error تانية مش متوقعة تـreturn 500 — من غير ما تبوظ الـ API أو تعمل Exception unhandled.
