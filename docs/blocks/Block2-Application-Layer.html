Application Layer

الـ Use Cases، الـ DTOs، وال Service Interfaces

ما اللي بنيناه في الـ Block ده

  • الـ DTOs الخاصة بالـ Users والـ Tasks (Request و Response)
  • الـ Service Interfaces اللي بتحدد كل الـ Use Cases

1
الـ Application Layer — وظيفتها إيه بالظبط؟

الـ Application Layer هي طبقة الـ Use Cases — يعني الأعمال اللي النظام بيعملها. هي اللي بتجاوب على سؤال: "إيه اللي التطبيق بيقدر يعمله؟"

RegisterUser، LoginUser، CreateTask، UpdateTaskStatus، DeleteUser... ده اللي موجود فيها.

إيه اللي الـ Application Layer مش بتعمله
  • مش بتعرف إزاي تعمل Hash للـ Password — ده شغل Infrastructure
  • مش بتعرف إزاي تولد JWT Token — ده شغل Infrastructure
  • مش بتعرف SQL أو EF Core أو Redis — ده كله Infrastructure
  • مش بتعرف إن في HTTP Request أصلاً — ده شغل الـ API Layer
هي بتعمل إيه بالظبط إذاً؟

بتـorchestrate بس — بتنسق بين الأجزاء:

  1. بتـvalidate الـ Input
  2. بتطبق الـ Business Rules
  3. بتنادي الـ Repository (عن طريق الـ Interface)
  4. بترجع النتيجة كـ DTO
2
الـ DTOs — ليه ما بنرجعش الـ Entity مباشرة؟

ممكن تفكر: "عندي Entity اسمها User، ليه أعمل UserResponse DTO تاني؟"

لأن إرجاع الـ Entity مباشرة من الـ API فيه مشاكل كتير:

❌ غلط — إرجاع Entity مباشرة
return Ok(user);
// سيريلايز الـ PasswordHash
// للـ Client !
✓ صح — إرجاع DTO
return Ok(new UserResponse
{
    Id = user.Id,
    Name = user.Name,
    Role = user.Role.ToString()
});
  • الـ User عنده PasswordHash — ما تبعتوش للـ Client أبداً
  • الـ User عنده Navigation Properties (Tasks) — بتعمل Circular Reference في الـ JSON Serializer
  • الـ Entities عندها private set — الـ JSON Serializer بيتعب معاها
  • شكل الـ Entity بتحدده قاعدة البيانات — شكل الـ API Response المفروض يتحدده احتياج الـ Client
ليه Role و Status و Priority بيبقوا string في الـ Response DTO؟
// داخلياً في الـ Entity — بتتخزن كـ Integer في الـ DB
public AppTaskStatus Status { get; set; }

// في الـ Response DTO — بتتبعت للـ Client كـ String
public string Status { get; set; }  // "Pending", "InProgress", "Done"

الـ API Consumers (موبايل، فرونت إند، سيرفيسز تانية) ما يعرفوش وما يهموش إن عندك Enum قيمته 1 أو 2. هما محتاجين يشوفوا "Pending" أو "High" — كلام بيتكلم عن نفسه. التحويل من الـ Enum للـ String بيحصل في الـ Service Layer.

3
Request DTOs vs Response DTOs

في نوعين من الـ DTOs — كل واحد بيتحرك في اتجاه مختلف:

الـ DTO الاتجاه بيحتوي على إيه
RegisterUserRequest Client ← Server ← Client Input خام (الـ Password كـ Plain Text)
LoginRequest Client → Server بيانات الدخول
CreateTaskRequest Client → Server بيانات الـ Task الجديدة
UpdateTaskStatusRequest Client → Server التغيير المطلوب فقط
UserResponse Server → Client بيانات المستخدم الآمنة
TaskResponse Server → Client بيانات الـ Task للعرض
💡 القاعدة الأساسية
الـ Request DTOs بتاخد Input خام (زي الـ Password كـ نص عادي).
الـ Response DTOs بترجع Output معالج وآمن — ما فيهاش Password Hash أبداً.
4
Service Interfaces — ليه Interface للـ Service؟
public interface IUserService
{
    Task<UserResponse> RegisterAsync(RegisterUserRequest request);
    Task<string>       LoginAsync(LoginRequest request);
    Task<UserResponse> GetByIdAsync(Guid id);
    Task<IEnumerable<UserResponse>> GetAllAsync();
    Task               DeleteAsync(Guid id);
}

نفس سبب وجود الـ Repository Interfaces في الـ Domain — الـ Dependency Inversion.

  • الـ Controller بيعتمد على IUserService مش على UserService
  • تقدر تبدل الـ Implementation من غير ما تلمس الـ Controller
  • تقدر تـmock الـ IUserService في الـ Unit Tests من غير ما تشغل DB حقيقية
ليه LoginAsync بترجع string؟

لأن نتيجة الـ Login هي JWT Token — مش أكتر من كده. الـ Controller بياخد الـ String ده ويحطه في الـ Response Body. مفيش داعي لـ DTO كامل هنا.

ليه بنمرر Guid userId في الـ Task Methods؟
Task<TaskResponse> GetByIdAsync(Guid id, Guid userId);

عشان نطبق الـ Ownership Rule: المستخدم يشوف Tasks بتاعته هو بس.

الـ userId بييجي من الـ JWT Token Claims اللي الـ Controller بيقراها. الـ Service بتتحقق إن الـ Task بـ id ده ملكه هو فعلاً. لو لأ، بترمي DomainException.

5
Common Infrastructure Contracts — فين الـ Interface يتحط؟
public interface IPasswordHasher
{
    string Hash(string password);
    bool   Verify(string password, string hash);
}

public interface IJwtTokenGenerator
{
    string GenerateToken(User user);
}

سؤال مهم: ليه الـ Interfaces دي موجودة في Application/Common/Interfaces ومش في الـ Infrastructure؟

لأن الـ Application Layer محتاجة تستخدمهم (في الـ UserService مثلاً). لو حطينا الـ Interfaces في الـ Infrastructure:

  • الـ Application هتحتاج Reference للـ Infrastructure
  • وده بيعكس اتجاه الـ Dependency — انتهاك صريح للـ Clean Architecture
✓ النمط الصح
Application بتعرّف الـ Contract (Interface): "أنا محتاج حاجة تعمل Hash للـ Passwords"
Infrastructure بتوفر الـ Implementation: BCryptPasswordHasher : IPasswordHasher
الـ DI Container بيربطهم وقت الـ Startup
6
تنظيم الـ Folders — Feature-Based مش Type-Based

ليه بننظم الـ Application Layer بالـ Feature (Users/, Tasks/) مش بالنوع (DTOs/, Interfaces/)؟

❌ Type-Based — مش مريح
Application/
├── DTOs/
│   ├── RegisterUserRequest.cs
│   ├── CreateTaskRequest.cs
│   └── UserResponse.cs
└── Interfaces/
    ├── IUserService.cs
    └── ITaskService.cs
✓ Feature-Based — كل حاجة في مكانها
Application/
├── Users/
│   ├── DTOs/
│   └── Interfaces/
└── Tasks/
    ├── DTOs/
    └── Interfaces/

الـ Feature-Based Organization = Vertical Slices. لما بتشتغل على الـ Users Feature، كل الملفات المتعلقة بيها في مكان واحد. مش بتقفز بين مجلد DTOs ومجلد Interfaces. وبيـscale كويس — لو ضفت Feature جديدة، بس ضيف Folder جديد.

!
أخطاء شائعة في الـ Block ده
Mistake Why It's Wrong Fix
Returning User entity from service Exposes PasswordHash, navigation props, serialization issues Return UserResponse DTO
Status as int in response DTO API consumer receives 1 instead of "Pending" Use string, map enum in service
IJwtTokenGenerator interface in Infrastructure Application would need to reference Infrastructure — violates Clean Architecture Put interface in Application/Common/Interfaces/
Task service method without userId Can't enforce ownership — any user could access any task Always pass userId extracted from JWT claims
Sync service methods DB calls underneath are async — sync wrapper blocks threads Always return Task<>
